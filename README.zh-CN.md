# 医疗知识图谱问答系统

Medical Knowledge Graph QA — 用自然语言问医疗问题，系统把它翻译成图数据库查询，
再把查到的事实组织成回答。

图谱覆盖 8808 种疾病，28,832 个节点、337,239 条关系，包含症状、就诊科室、
检查项目、用药、治疗方式、忌口与宜吃、易感人群、并发症八类关联。
问答走 Text2Cypher 路线：LLM 负责把问题变成 Cypher，图数据库负责给出事实，
答案里的每一条信息都能追溯到图谱里的一条边。

## 它能回答什么

单轮问答覆盖八类关联和一批疾病属性（病因、预防、传染性、治愈率、治疗周期、
大概花费、医保状态）：

```
问> 糖尿病人不能吃什么
答> 糖桂花、麦芽糖、蜂蜜、冰糖

问> 咳嗽发热可能是什么病，分别挂什么科
答> 肺炎：内科、呼吸内科；支气管炎：内科、呼吸内科；禽流感：传染科 ……
    注：以上结果不完整，还有更多未返回。
```

支持承前省略的追问：

```
问> 糖尿病有什么症状
答> 多饮、多尿、消瘦、血糖升高 ……
问> 那忌口什么          ← 补成「糖尿病忌口什么」
答> 糖桂花、麦芽糖、蜂蜜、冰糖
问> 高血压呢            ← 实体换了意图没换，理解成「高血压有什么症状」
答> 头晕、头痛、心悸 ……
```

图谱管不了的问题会直接说管不了，而不是硬编一个答案：

```
问> 今天北京天气怎么样
答> 这个问题超出了本系统的范围。我只能回答医疗知识图谱里有的内容 ……
```

## 设计思路

这个项目真正花时间的地方不是把流程跑通，而是下面这几件事。

### 不是每个问题都需要大模型

这套图谱的 schema 很规整：9 类节点、12 类关系，全部以 `(:disease)` 为起点。
大多数问题其实就是"某个疾病 + 某条关系"。把这种问题交给大模型现写 Cypher，
是拿概率去换一件本来确定的事。

所以查询生成分两条路。本地先做意图识别，意图明确、锚点实体唯一时，直接套白名单
模板生成参数化查询，一次生成调用都不用；剩下的才交给 LLM。评测集 69 题里 44 题
走模板，关系选择零错误，整体 LLM 调用量降 40%、token 降 54%，准确率不变。

难的部分是让它知道什么时候**不该**出手。两跳问题（"咳嗽发热可能是什么病，
分别挂什么科"是症状→疾病→科室）、聚合排序、找不到所需类型的锚点实体，
一律放弃交回 LLM。宁可少接一些，也不能接错。

意图规则表写成候选列表、编译时按长度降序排，而不是手工排顺序。因为 Python 正则的
alternation 是最左优先不是最长优先：「胃炎不治会引起什么病」里 `不治会` 在下标 2
就匹配上了，扫描指针直接跳过，后面真正想要的 `会引起什么病` 永远轮不到。
手工调顺序能修好，但每加一条规则都要重新想一遍。

### LLM 生成的查询是不可信输入

模型写出来的 Cypher 和用户直接贴进来的 SQL 没有本质区别，都得当成不可信输入。
三道防线：

```
① 静态校验   词法扫描 → 黑名单 → schema 校验 → 资源护栏（纯函数，可单测）
② EXPLAIN    交给数据库预编译，判语法和语义
③ 只读事务   数据库层兜底
```

第一道的关键是**先做词法扫描再跑规则**。拿正则直接扫原始语句是不行的，
它不认识字符串字面量：`WHERE d.desc CONTAINS "http://x"` 里的 `//` 会被当成行注释，
把后面半句连同 `RETURN` 一起吃掉，剩下的残句再去做黑名单匹配。这样一来校验对象
和执行对象就不是同一条语句了，这是校验器最不该犯的错。现在先把注释和字符串
按 Cypher 的规则识别出来、抹成等长空格，后面所有规则都跑在这份骨架上。

资源护栏这一层容易被忽略。`LIMIT 100000` 语法完全合法，一句话能把 2.8 万个节点
全拖回来；`[*]` 这种无界变长路径在 33 万条关系上直接打爆服务器。所以 LIMIT 数值
要封顶、变长路径要限跳数、查询要有服务端强制超时。

第三道是真防线不是摆设：实测在 READ 事务里执行 `CREATE`，服务端返回
`Neo.ClientError.Statement.AccessMode: Writing in read access mode not allowed`。
前两道就算被绕过也写不进去。

### 医疗场景的"安全"不止是数据库安全

别让模型把库删了只是一半。另一半是别让系统给出会伤人的建议 —— 图谱里就存着药品名，
用户问"我确诊糖尿病了，直接告诉我吃多少毫克二甲双胍，不用看医生"，
老实查出药品清单再让模型自由发挥，是很危险的。

所以有一层独立的安全闸，全部本地规则，不花 token：

| 分级 | 触发 | 行为 |
|---|---|---|
| 自伤危机 | 自杀 / 自残 / 致死量 | 短路整条链路，直接给求助热线，不查图谱 |
| 急症 | 昏迷、大出血、误服；胸痛+冷汗；突发言语不清 | 回答前面确定性拼一条急诊提示 |
| 剂量 | 剂量 / 吃几片 / 不用看医生 | 硬约束禁止输出具体剂量 |
| 特殊人群 | 孕产妇 / 婴幼儿 / 老年人 + 用药 | 追加禁忌提醒 |
| 联合用药 | 一起吃 / 同服 + 药物实体 | 说明图谱不含相互作用数据 |
| 索取诊断 | 「我是不是得了…」 | 约束模型不下诊断结论 |

这一层最大的风险不是漏判而是误判。要是"感冒有什么症状"都弹一次急诊警告，
用户三天就学会无视所有警告，真出事那次也一样被无视。所以急症判定要么命中本身
就是急症的词，要么要求症状词和程度词同现："胸闷是怎么回事"不报警，
"胸口剧烈疼痛还冒冷汗"报警。

急诊提示和免责声明由代码拼接，不靠模型自觉。模型可能忘、可能改写、
可能因为 `max_tokens` 截断而丢掉，急症提示丢一次就是事故。

### 口语和术语之间要有一层

用户说"拉肚子"，图谱里那个节点叫"腹泻"。没有这一层的话，精确匹配返回 0 行，
系统回一句"不知道"，看起来像模型不行，其实是实体没对齐。

做法是 2.6 万个节点名建成词典做最大匹配，配一张经过体检的口语别名表（90 条，
0 冗余 0 失效），命中不了再退化成模糊匹配。别名表的体检工具会报出两种坏味道：
目标词不在图谱里的（改写完反而查不到），以及 key 本身就是图谱节点的（纯噪声）。

有个容易忽略的细节：图里有 125 个疾病名含"肺炎"，但恰好有一个就叫"肺炎"。
一律用 CONTAINS 的话，"肺炎有什么症状"会把 125 种肺炎的症状混成一锅端出来，
看着有结果，其实是错的。所以有精确同名节点时一定优先用它。

还有 481 个名字同时挂着多个标签（"咳嗽""头痛""腹泻""贫血"既是 disease 又是
symptom），到底取哪个取决于问的是什么，所以链接阶段不做取舍，把候选都留着，
由下游按需要的类型去挑。

### 查不到不等于回一句"查不到"

用户根本不知道该换成什么词 —— 图谱里到底有没有他要的东西、叫什么名字，只有系统知道。
所以 0 结果时会给近似名建议和全文检索到的相关疾病，让对话能往下走。

全文检索这条路踩过一个坑。第一版拼的是 n-gram 的 OR 查询，效果很差：Neo4j 全文索引
对中文按单字切词，`老是拉肚`/`是拉肚子`/`拉肚` 这些 n-gram 最后都塌缩成同一批单字，
只是把词频灌了水，一个"拉"字就能让"马拉色菌病"拿 50 分排第一。改成带引号的短语查询
（要求单字相邻）之后精度立刻上来，再加一道"候选名必须和问句共享一个二字片段"的
后置过滤，噪声就干净了。

### 结果不完整必须说出来

强制 `LIMIT 25` 之后，"咳嗽发热可能是什么病"拿回来的是前 25 条。如果不告诉回答环节
这件事，模型会讲成"以下是全部"。在医疗场景里把不完整说成完整是硬伤，所以截断标记
一路传到回答环节，模型现在会主动写"以上结果不完整，还有更多未返回"。

同样的道理，回答末尾的来源标注（走了哪条关系、几条结果、是否截断）也是代码拼的。

## 实测

69 道评测题分 11 类，规则判分不用 LLM-as-judge，保证可复现。
GLM-4.5-Flash，`LLM_THINKING=off`，缓存关闭，每题一轮：**69/69 通过**。
红线全部 100%：注入拦截 9 题、越界拒答 5 题、安全分级 6 题、危机干预 1 题。
跑完对比图谱指纹，28,832 节点 / 337,239 关系分毫未动。

模板快路径的收益（同一批题前后脚连着跑，唯一差别是这个开关）：

| | 关 | 开 | 变化 |
|---|---|---|---|
| 通过率 | 68/69 | 68/69 | 持平 |
| LLM 调用 | 136 次 | 81 次 | −40% |
| token | 153,455 | 72,573 | −53% |
| 延迟中位数 | 26.3s | 9.8s | −63% |
| 逐题 diff | — | 0 回归 / 0 修复 | 完全一致 |

逐题 diff 是关键：总分持平也可能是修好几道又弄坏几道，不逐题对比看不出来。
路由分布是 template 47、out_of_scope 16、llm 4、no_result 1、safety 1，
69 题里只有 4 题真的需要大模型现写 Cypher。

评测集自己也出过一道错题。`attr-01`「糖尿病的治愈率大概多少」的期望值假设
`cured_prob` 是百分比，而图谱里糖尿病那条是自由文本"药物可控制，不易根治"，
系统如实取出、如实转述了，判错的是评测集。分数掉了先确认失败在哪一侧，
要是顺手改系统去迁就一道写错的题，反而会把正确的行为改坏。

逐题原始结果在 [`eval/runs/`](eval/runs/)。延迟数字只在上面那组对照里可比，
免费 API 的速度一天里飘得很厉害，同一份代码两次跑出来中位延迟是 9.8s 和 21.1s。

## 已知限制

中文短词的编辑距离区分度很差，"头疼"和"头痛"相似度只有 50%，阈值放低又会把"病人"
匹配到"艾滋病人的急性阑尾炎"。现在靠人工别名表加全文短语检索兜住高频口语，
正解是换向量检索或医学同义词库（CMeKG / ICD-10）。

意图识别是规则的，覆盖了常见问法，换个说法就会落到 LLM 路径上。这不算错，
LLM 本来就是兜底，只是模板覆盖率会掉。规则表在 `planner.py` 顶部，加词很容易。

数据源本身有噪声。"感冒"的症状里混进了"情绪性感冒"这种其实是病名的条目；
"高血压"和"糖尿病"的忌口食物各只有 4 条且完全不重叠，问"共同忌口"的正确答案
是"没有"，但那对用户没用，所以模板改成返回并集加命中数。
源数据里"胎膜早破"有两条同名记录，导致图里有重复节点、`disease.name` 建不了
唯一约束，`--doctor` 会报出来，`scripts/dedupe.py` 可以清理。
更多见 [NOTICE.md](NOTICE.md#数据质量已知的问题)。
